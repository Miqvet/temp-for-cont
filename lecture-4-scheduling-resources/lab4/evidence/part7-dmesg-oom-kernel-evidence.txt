- constraint=CONSTRAINT_MEMCG + the cgroup path ending in the pod's own
  cri-containerd-<id>.scope (not the node's root/kubepods-level cgroup) means
  both kills were scoped to the INDIVIDUAL CONTAINER's own memory cgroup —
  i.e. "OOMKilled by own limit", not a whole-node eviction.
- anon-rss ~2091504-2091828kB (~2044MiB) sits right at the container's
  resources.limits.memory: 2Gi (2048Mi) — confirms the container was killed
  for exceeding ITS OWN declared limit, consistent with the memcg scope.
- oom_score_adj=990 is exactly what kubelet sets for a Burstable pod whose
  request is far below its limit (close to the BestEffort end of the scale,
  990 out of a max of 1000) — this is the mechanism (not kubelet's soft
  eviction manager) that would make batch the preferred kernel OOM victim
  over api/postgres (Guaranteed, oom_score_adj=-997) if a REAL whole-node
  OOM ever occurred instead of a per-pod one.
- kubectl's own status.containerStatuses[].lastState.terminated.reason showed
  the generic string "Error" (not "OOMKilled") for both kills, exit code 137.
  dmesg is the only place the kill is unambiguously confirmed as OOM — see
  README, Part 7, for why this matters.
